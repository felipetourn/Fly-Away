## Qué se hizo

La venta ya descontaba los asientos bajo un bloqueo del vuelo desde la US08, pero nunca se había probado con operaciones realmente simultáneas: los tests corren en SQLite, que no bloquea filas. En esta US se analizaron los escenarios de concurrencia, se dejó escrito el mecanismo y se probó con hilos reales contra Postgres.

**Mecanismo:** bloqueo pesimista de la fila del vuelo (`select_for_update()` dentro de `transaction.atomic()`) en toda operación que lee o cambia su disponibilidad; descuento con `F()` solo al confirmar el pago; el pago se bloquea después del vuelo y, si ya no está pendiente, no se vuelve a confirmar. Respaldo en la base: `CHECK asientos_disponibles_* >= 0` y un solo pago aprobado por reserva. La tabla de escenarios está en [arquitectura.md](../../arquitectura.md#concurrencia-us11).

**Liberación de lugares:** una reserva pendiente o un pago rechazado nunca toman asientos (se descuentan recién al aprobar), así que no hay nada que liberar si la operación se cancela o falla.

**Mensajes:** quien pierde el último lugar mientras paga con tarjeta ve "Se vendieron los últimos lugares de este vuelo mientras pagabas. No se hizo ningún cobro."; si fue con Mercado Pago, el resultado del pago dice "Se vendieron los últimos lugares mientras pagabas: corresponde devolución."

## Criterios de aceptación

| Criterio | ¿Cumple? | Evidencia |
| -------- | -------- | --------- |
| Los pasajes vendidos nunca superan la capacidad del vuelo y clase | ✅ | `test_muchos_compradores_nunca_sobrevenden`: 20 compradores piden 39 lugares de 10 |
| Con un solo lugar, dos operaciones concurrentes no confirman ambas | ✅ | `test_ultimo_lugar_dos_tarjetas_a_la_vez`, `test_ultimo_lugar_dos_aprobaciones_de_mp_a_la_vez` |
| Una operación confirmada actualiza correctamente la disponibilidad | ✅ | `test_mismo_pago_confirmado_dos_veces_a_la_vez` (10 → 8), `ConfirmacionTests` |
| Una operación rechazada o cancelada no reduce definitivamente la disponibilidad | ✅ | `test_rechazos_y_fallas_no_reducen_la_disponibilidad` |
| Si pierde la disponibilidad en curso, el usuario recibe información clara | ✅ | `test_sin_lugar_explica_que_se_vendieron_mientras_pagaba`; el front muestra el mensaje en la pantalla de pago y en el resultado |
| Una misma transacción no genera más de una compra confirmada | ✅ | `test_mismo_pago_confirmado_dos_veces_a_la_vez`: un aprobado, una factura |
| Tras múltiples operaciones concurrentes, vendidos y disponibles son consistentes | ✅ | `test_muchos_compradores_nunca_sobrevenden`: vendidos + disponibles = 10 |
| El control se realiza sobre la instancia particular del vuelo y clase | ✅ | `test_ultimo_lugar_de_economy_no_toca_primera_ni_otra_fecha` |

Para comprobar que las pruebas sirven, se quitaron los `select_for_update()` de `pagos/servicios.py`: las cuatro pruebas concurrentes fallaron. Con el bloqueo pasaron cinco corridas seguidas, y la suite completa del backend también pasa en Postgres.

## Cómo probarlo

1. Suite normal (SQLite; las pruebas concurrentes figuran como *skipped*):
   ```bash
   cd backend
   DATABASE_URL= .venv/bin/python manage.py test
   ```
2. Pruebas concurrentes: con un Postgres local (no el de Supabase),
   ```bash
   DATABASE_URL=postgres://postgres@localhost:5432/postgres .venv/bin/python manage.py test pagos.tests_concurrencia
   ```
3. A mano: dejar un vuelo con 1 lugar en economy, abrir dos navegadores con dos pasajeros que tengan una reserva de ese vuelo y pagar con `4242 4242 4242 4242` en los dos. Uno ve "¡Compra confirmada!" y el otro el mensaje de que se vendieron los últimos lugares.
